# VYOM — Phase 5: Complete Product Functionality, Website Engineering & Live End-to-End Validation

## Mission

Transform VYOM into a fully functional, polished, reliable digital-wallet application by auditing, implementing, testing, and validating every user-facing feature and its complete backend integration.

This is a product-completion and reliability phase.

The objective is not simply to make the website look attractive. Every page, button, form, interaction, transaction flow, error state, navigation element, and displayed financial value must work correctly.

You are responsible for understanding the existing architecture, defining the expected behavior of every feature, identifying incomplete or incorrect functionality, implementing necessary fixes, launching the complete application, and validating it through real browser interactions and backend/database verification.

**Do not declare completion because the application starts or because automated unit tests pass. Completion requires successful end-to-end validation of the actual running application.**

---

# PART 1 — NON-NEGOTIABLE ENGINEERING RULES

### 1. Preserve the architecture

The existing architecture is:

Browser (HTML/CSS/JavaScript) → Node.js/Express Gateway → Java/Spring Boot Backend → PostgreSQL.

Preserve this architecture.

- Java/Spring Boot remains the financial business-logic authority.
- PostgreSQL remains the source of truth for balances, transactions, and ledger records.
- Express remains the gateway.
- The browser must never independently calculate or determine authoritative financial balances.
- Do not move financial logic into JavaScript.
- Do not introduce microservices.
- Do not introduce Kafka, RabbitMQ, Redis, or Kubernetes without a separately justified architectural requirement.
- Do not replace working components simply to use a different technology.

### 2. Financial correctness takes priority over UI convenience

Every financial operation must preserve:

- Double-entry accounting.
- Atomicity.
- Idempotency.
- Currency precision.
- Wallet ownership.
- Authentication and authorization.
- Immutable financial history.
- Correct transaction status.
- Consistent balance and ledger state.

Never sacrifice financial correctness to make an interface appear responsive.

### 3. No fabricated functionality

Do not display fake transaction histories, fake balances, fake payment confirmations, fake analytics, or hardcoded success notifications.

All financial information must originate from actual backend responses.

If a feature is not supported by the backend, identify that limitation. Do not simulate a successful backend operation in the frontend.

VYOM is a simulated wallet platform. Do not claim real UPI, bank, or payment-gateway integration.

### 4. No blind changes

Before modifying anything:

1. Inspect the repository.
2. Identify the existing frontend pages and components.
3. Inspect the actual gateway routes.
4. Inspect the backend controllers, services, DTOs, entities, and security rules.
5. Inspect database migrations and existing transaction semantics.
6. Map each existing frontend operation to its actual backend endpoint.
7. Identify missing, broken, inconsistent, and misleading functionality.

Do not assume that an endpoint, feature, or permission exists merely because its name sounds plausible.

# PART 2 — DEFINE THE COMPLETE WEBSITE EXPERIENCE

First, produce a complete feature inventory and expected-behavior specification.

Then implement and validate the following functional areas.

## 1. Landing page

Expected behavior:

- Clearly communicate what VYOM is.
- Explain that it is a digital wallet and transaction-processing platform.
- Present the product's primary capabilities.
- Provide functional Login and Register navigation.
- Provide an understandable explanation of the simulated wallet model.
- Maintain consistent visual language throughout the application.
- Avoid exaggerated claims about real banking integrations or production financial infrastructure.

All navigation links must lead to valid destinations.

No decorative button should appear clickable unless it actually performs an action.

## 2. Registration

The registration process must:

1. Accept the required user details supported by the backend.
2. Validate required fields.
3. Validate email format.
4. Validate password requirements.
5. Provide password visibility controls.
6. Prevent repeated submissions while a request is processing.
7. Display field-specific validation errors.
8. Handle duplicate accounts correctly.
9. Display meaningful backend errors.
10. Navigate to the appropriate next step only after successful registration.

Security requirements:

- Never expose password hashes.
- Never store plaintext passwords.
- Never silently create a user in the frontend.
- Do not permit users to register themselves with administrative privileges.
- Do not leak sensitive backend exception details.

Test duplicate registration, invalid input, network failure, and successful registration.

## 3. Login and authentication

Expected behavior:

- Accept valid credentials.
- Authenticate through the actual backend.
- Store the authentication token only according to the existing secure frontend design.
- Do not move tokens into localStorage or sessionStorage merely for convenience.
- Restore the authenticated interface only if the existing architecture securely supports it.
- Provide a proper logout operation.
- Handle expired and invalid tokens.
- Handle unauthorized API responses consistently.
- Redirect unauthenticated users away from protected pages.

Test:

- Valid login.
- Invalid password.
- Unknown account.
- Empty credentials.
- Expired token.
- Invalid token.
- Logout.
- Direct navigation to a protected page without authentication.
- Browser refresh after authentication.

The interface must never continue displaying private account information after logout.

## 4. Dashboard

The dashboard must show actual information returned by the backend.

Expected components:

- Total available wallet balance.
- Currency.
- Recent transactions.
- Transaction counts or summaries, if supported by actual APIs.
- Quick actions for supported operations.
- Account information.
- Relevant transaction statuses.

Functional requirements:

- Refreshing the dashboard must retrieve current backend data.
- Loading indicators must be shown during requests.
- Empty states must be understandable.
- API failures must not be represented as zero balances.
- Stale data must not be presented as freshly retrieved data.
- Dashboard values must reconcile with wallet and transaction details.

Test dashboard behavior with:

- A newly registered account.
- An account with no transactions.
- An account with funding history.
- An account with transfers.
- An account with refunds.
- Backend unavailable.
- Authentication expired.

## 5. Wallet details

The wallet interface must:

- Display actual wallet information.
- Display the correct currency.
- Show the current authoritative balance.
- Avoid floating-point arithmetic for money.
- Display monetary amounts using the correct decimal representation.
- Handle empty and unavailable states.
- Refresh after completed financial operations.

Never calculate the displayed balance by adding or subtracting amounts in frontend state and treating that result as authoritative.

If optimistic UI is used for non-financial interface elements, it must never create a false financial success state.

## 6. Wallet funding

Expected user journey:

1. User opens the funding page.
2. User enters a valid amount.
3. The application validates the amount.
4. The user reviews the funding operation.
5. The user explicitly confirms it.
6. The frontend submits the request through the gateway.
7. The backend processes the funding operation atomically.
8. The application retrieves the resulting authoritative transaction and balance.
9. The user sees a success confirmation only after the backend confirms completion.

Requirements:

- Positive amounts only.
- Respect supported currency precision.
- Reject malformed values.
- Prevent accidental duplicate submissions.
- Use a stable idempotency key for a logical operation.
- Preserve that key when retrying the same operation after an ambiguous network failure.
- Do not generate a new key simply because the first request timed out.
- Distinguish a failed operation from an operation whose final commit status is unknown.
- Never show success merely because the HTTP request was initiated.

Validate that the funding operation creates the correct double-entry journal involving the system settlement account and the customer wallet.

## 7. Money transfers

Expected user journey:

1. User selects the transfer feature.
2. User enters the recipient identifier supported by the backend.
3. User enters the amount.
4. User enters an optional description, if supported.
5. Application validates the request.
6. Application displays a review/confirmation step.
7. User confirms.
8. Gateway forwards the authenticated request.
9. Backend verifies ownership, authorization, balance, and other applicable business rules.
10. Backend performs the atomic financial operation.
11. Application displays the final transaction outcome.
12. Wallet balance and transaction history refresh from the backend.

Requirements:

- Do not allow self-transfer if prohibited by backend rules.
- Do not allow negative or zero amounts.
- Do not permit transfers beyond available balance.
- Do not expose another user's private wallet information.
- Display appropriate errors for nonexistent recipients.
- Handle concurrent transfers safely.
- Prevent duplicate transfers through idempotency.
- Handle timeouts without accidentally creating a second transfer.
- Display correct sender and recipient perspectives.
- Preserve the original transaction reference.

Test successful transfers, insufficient balance, invalid recipient, self-transfer, duplicate requests, simultaneous requests, and ambiguous timeouts.

## 8. Transaction history

Expected behavior:

- Retrieve transactions from the backend.
- Display accurate transaction references.
- Display transaction type.
- Display amount and currency.
- Display date and time.
- Display transaction status.
- Display the appropriate sender/recipient perspective.
- Support pagination if the backend provides it.
- Preserve pagination state correctly.
- Handle empty results.
- Handle API failures.
- Avoid duplicate records across pages.

If filters are supported, implement and validate them against actual backend capabilities.

Never generate transaction history from frontend-only data.

## 9. Transaction details and receipts

When a user opens a transaction:

- Display the correct transaction reference.
- Display the amount and currency.
- Display the transaction type.
- Display the current recorded status.
- Display the timestamp.
- Display the appropriate transaction parties.
- Display the description if available.
- Display available receipt information.

Ownership must be enforced by the backend.

Users must not be able to access another user's transaction simply by changing an identifier in the URL.

A receipt must accurately represent the backend transaction. Do not manufacture a receipt for an uncommitted operation.

## 10. Refunds and reversals

Inspect the actual backend capabilities before implementing these interfaces.

Where supported:

- Display eligible transactions.
- Display refund information.
- Display refund status.
- Display refund history.
- Clearly distinguish a refund from a reversal.
- Display partial and complete refunds accurately.
- Prevent refund amounts from exceeding the remaining refundable amount.
- Handle already-refunded and reversed transactions.
- Display the actual resulting transaction references.

Authorization requirements:

- Administrative reversal operations must remain administrator-only.
- Normal users must never gain administrative functionality through frontend manipulation.
- The backend must independently enforce permissions.

Do not add a frontend refund or reversal action if no corresponding secure backend operation exists.

## 11. Disputes

If the backend dispute feature is available:

- Allow users to view their eligible transactions.
- Allow dispute creation where permitted.
- Collect the supported dispute reason and description.
- Display submission status.
- Display existing dispute details.
- Prevent duplicate active disputes where prohibited.
- Do not change wallet balances merely because a dispute was created.
- Do not imply that a dispute automatically reverses a transaction.

Display only real dispute information returned by the backend.

## 12. Profile and account information

Where supported:

- Display the authenticated user's account information.
- Display the appropriate wallet information.
- Allow supported profile updates.
- Validate inputs.
- Handle update failures.
- Prevent unauthorized account modifications.

Never expose internal IDs, passwords, tokens, roles, or sensitive implementation information unnecessarily.

## 13. Administrative functionality

Inspect the existing role-based backend capabilities.

If an admin interface exists or is required by existing functionality:

- Separate administrator navigation from normal-user navigation.
- Display only authorized administrative operations.
- Enforce all permissions on the backend.
- Display reversal functionality only to authorized administrators.
- Handle forbidden responses.
- Never rely on hiding a button as the authorization mechanism.

Test normal-user and administrator accounts independently.

# PART 4 — ERROR HANDLING AND FAILURE RECOVERY

This is a financial application. Failure behavior is as important as success behavior.

Test and implement correct handling for:

- Backend unavailable.
- Gateway unavailable.
- Database unavailable.
- Request timeout.
- HTTP 400.
- HTTP 401.
- HTTP 403.
- HTTP 404.
- HTTP 409.
- HTTP 422, if used.
- HTTP 429.
- HTTP 500.
- HTTP 502.
- HTTP 503.
- HTTP 504.
- Malformed JSON.
- Unexpected response format.
- Expired authentication.
- Duplicate submission.
- Ambiguous financial operation outcome.

### Critical timeout rule

If a financial operation times out:

- Do not automatically assume it failed.
- Do not automatically assume it succeeded.
- Preserve its original idempotency key.
- Query the appropriate transaction/idempotency status if the backend supports it.
- Retry only under the existing idempotency contract.
- Display an honest pending or unknown status when the outcome cannot yet be established.

Never encourage the user to submit a second independent payment simply because the first request timed out.

# PART 7 — LIVE END-TO-END TEST SCENARIOS

Build a repeatable browser-level test suite.

At minimum, execute the following journeys.

### Journey A — New user

1. Open landing page.
2. Navigate to registration.
3. Register a new normal user.
4. Attempt duplicate registration.
5. Log in.
6. Open dashboard.
7. Open wallet.
8. Log out.
9. Attempt protected-page access.

### Journey B — Funding

1. Log in as User A.
2. Record the initial authoritative balance.
3. Fund the wallet with a valid amount.
4. Verify the backend response.
5. Verify the transaction record.
6. Verify both ledger entries.
7. Verify the resulting balance.
8. Verify dashboard refresh.
9. Verify transaction history.
10. Retry the original idempotency key and confirm no duplicate financial operation.

### Journey C — Successful transfer

1. Register or use User A and User B.
2. Fund User A.
3. Record both wallet balances.
4. Transfer a valid amount from A to B.
5. Verify transaction status.
6. Verify sender and recipient balances.
7. Verify the double-entry journal.
8. Verify both users see the correct transaction perspective.
9. Verify the transaction receipt.

### Journey D — Failed transfer

Test:

- Insufficient balance.
- Invalid recipient.
- Invalid amount.
- Zero amount.
- Negative amount.
- Duplicate submission.
- Unauthorized request.
- Expired token.

Verify that failed operations do not create incorrect financial records or alter balances.

### Journey E — Concurrent operations

Execute simultaneous transfers and funding operations through the real gateway.

Verify:

- No duplicate financial operation.
- No lost balance updates.
- No negative balances where prohibited.
- Correct idempotency behavior.
- Correct transaction statuses.
- Successful database reconciliation.

### Journey F — Timeout and recovery

Create a controlled test that causes an actual gateway/client timeout while the backend may still complete the financial operation.

Then retry using the same idempotency key.

Verify the final database state and prove that the same logical operation was not committed twice.

Do not simulate a timeout by merely returning a fake frontend error.

### Journey G — Transaction history and receipt

Verify:

- Pagination.
- Transaction detail.
- Correct transaction reference.
- Correct amount and currency.
- Correct transaction status.
- Correct ownership enforcement.
- Correct receipt content.

### Journey H — Refund, reversal, and disputes

Execute only operations supported by the actual backend.

Verify their authorization, ledger effects, statuses, and UI representation.

### Journey I — Failure recovery

While the application is running:

- Temporarily make the backend unavailable.
- Test gateway health.
- Attempt a safe read.
- Restore the backend.
- Verify recovery.
- Test rate limiting.
- Test expired authentication.
- Test a failed network request.

Do not interrupt the database during active financial writes unless the experiment is explicitly isolated and designed to test that scenario.

# PART 8 — BUG DISCOVERY AND ITERATIVE REPAIR

Use the following mandatory debugging loop:

**Observe → Reproduce → Diagnose → Fix → Regression test → Full revalidation.**

For every discovered defect:

1. Assign a unique bug ID.
2. Record the affected feature.
3. Record reproduction steps.
4. Record expected behavior.
5. Record actual behavior.
6. Identify the root cause.
7. Identify the responsible layer: frontend, gateway, backend, database, or integration.
8. Implement the smallest safe correction.
9. Add a regression test.
10. Rerun the affected end-to-end journey.
11. Rerun relevant backend and gateway tests.
12. Verify that financial reconciliation remains correct.

Do not patch symptoms without understanding the root cause.

Do not repeatedly change code until a test happens to pass.

Do not weaken assertions, disable tests, remove security controls, or hide errors to obtain a passing result.

### Reinforcement learning instruction

Do NOT use reinforcement learning to modify application code or financial behavior.

Do not use an autonomous agent that continuously changes the application without review and reproducible tests.

Instead, use controlled iterative debugging and test-driven repair. Automation may assist with identifying and reproducing failures, but all code changes must remain reviewable, deterministic, and covered by regression tests.
